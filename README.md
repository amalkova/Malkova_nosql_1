# MongoDB Spotify Analytics

Домашнє завдання з NoSQL: робота з MongoDB Atlas, Aggregation Pipeline, запитами до вкладених документів та масивів, аналітичними агрегаціями й індексами.

У роботі використовується Spotify Tracks Dataset з Kaggle, який містить приблизно 114 000 треків.

---

## Структура проєкту

```text
.
├── .env
├── .gitignore
├── requirements.txt
├── scripts/
│   ├── 01_load_data.py
│   └── 02_transform.js
├── queries/
│   ├── part2_queries.js
│   ├── part3_aggregations.js
│   └── part4_indexes.js
└── README.md
```

Файл `.env` містить рядок підключення до MongoDB Atlas та не додається до Git-репозиторію.

# Частина 1 — Завантаження та схема даних

Початкові записи з CSV спочатку завантажуються до `tracks_raw`, після чого Aggregation Pipeline створює структуровану колекцію `tracks`.

Приклад документа:

```json
{
  "track_id": "5SuOikwiRyPMVoIQDJUgSV",
  "track_name": "Comedy",
  "album_name": "Comedy",
  "explicit": false,
  "popularity": 73,
  "duration_ms": 230666,
  "track_genre": "acoustic",
  "artists": [
    "Gen Hoshino"
  ],
  "audio_features": {
    "danceability": 0.676,
    "energy": 0.461,
    "loudness": -6.746,
    "speechiness": 0.143,
    "acousticness": 0.0322,
    "instrumentalness": 0.00000101,
    "liveness": 0.358,
    "valence": 0.715,
    "tempo": 87.917,
    "key": 1,
    "mode": 0,
    "time_signature": 4
  },
  "duration_sec": 230.7,
  "popularity_tier": "high"
}
```

## 1. Чому `audio_features` винесені в окремий вкладений об'єкт?

Поля `danceability`, `energy`, `tempo`, `valence`, `loudness`, `speechiness`, `instrumentalness` та інші описують одну логічну сутність — аудіо-характеристики треку.

Тому вони об'єднані у вкладений документ:

```text
audio_features
```

Це робить структуру документа більш зрозумілою: основна інформація про трек відокремлена від технічних характеристик аудіо.

Наприклад, звернення до характеристик має вигляд:

```javascript
"audio_features.energy"
"audio_features.danceability"
"audio_features.tempo"
```

Таке вкладення вигідне, коли набір полів логічно належить одному об'єкту та часто використовується разом.

Недоліком є те, що у запитах та індексах потрібно використовувати повний шлях до вкладеного поля. Якщо структура стає дуже глибокою або часто змінюється, це може ускладнювати запити та підтримку схеми.

---

## 2. Чому `artists` зберігається як масив, а не як рядок?

Один трек може мати одного або декількох виконавців.

Наприклад:

```json
{
  "artists": [
    "Roberto Diana",
    "Muniesa"
  ]
}
```

Масив дозволяє MongoDB працювати з кожним артистом як з окремим значенням.

Завдяки цьому простішими стають:

- пошук усіх треків конкретного артиста;
- використання `$unwind`;
- групування статистики за артистами;
- аналіз колаборацій декількох виконавців;
- підрахунок кількості треків кожного артиста.

Якби виконавці зберігалися одним рядком, його довелося б додатково розбирати під час аналізу.

---

## 3. Що таке `$out` і чим він відрізняється від `$merge`?

`$out` записує результат Aggregation Pipeline у вказану колекцію.

У цій роботі він використовується для створення колекції:

```text
tracks
```

на основі:

```text
tracks_raw
```

При повторному виконанні pipeline результат колекції фактично формується заново.

`$merge` працює інакше. Він дозволяє об'єднати результати pipeline з уже існуючою колекцією.

`$merge` доцільний, коли потрібно:

- оновлювати існуючі документи;
- додавати нові документи;
- виконувати інкрементальне оновлення;
- не перебудовувати всю колекцію повністю.

У цьому завданні `$out` є зручним, тому що `tracks` повністю створюється з `tracks_raw`.

# Частина 2 — Запити до даних

Запити знаходяться у файлі:

```text
queries/part2_queries.js
```

Реалізовано чотири завдання:

1. пошук треків для вечірки;
2. пошук артистів, у яких усі треки популярні;
3. визначення треків з нетипово високим tempo для жанру;
4. пошук музики для фонового прослуховування під час роботи.

---

## Завдання 1 — Треки для вечірки

Вибираються треки, що мають:

```text
danceability > 0.7
energy > 0.7
duration_ms від 180000 до 300000
```

Це відповідає тривалості приблизно від 3 до 5 хвилин.

---

## Завдання 2 — Виконавці, у яких усі треки популярні

Для кожного артиста обчислюються:

- кількість треків;
- мінімальна популярність;
- середня популярність.

У результат включаються артисти, які мають щонайменше 3 треки та мінімальну популярність не нижче 60.

---

## Завдання 3 — Нетипові треки

Для кожного жанру обчислюються:

```text
average tempo
standard deviation
```

Порогове значення:

```text
threshold = average tempo + 2 × standard deviation
```

Трек вважається нетиповим, якщо:

```text
track tempo > threshold
```

Для стандартного відхилення використовується:

```javascript
$stdDevPop
```

---

## Завдання 4 — Треки для фонової роботи

Вибираються треки, які відповідають умовам:

```text
loudness < -10
speechiness < 0.1
instrumentalness > 0.5
explicit = false
```

---

## 1. Для чого використовується `$unwind`?

`$unwind` розкладає масив на окремі документи у межах Aggregation Pipeline.

Наприклад:

```json
{
  "artists": [
    "Artist A",
    "Artist B"
  ]
}
```

після:

```javascript
{
  $unwind: "$artists"
}
```

буде представлений у pipeline як два окремі записи:

```text
Artist A
Artist B
```

Це дозволяє потім використовувати:

```javascript
$group
$avg
$min
$max
$count
```

окремо для кожного артиста.

У цій роботі `$unwind` використовується для побудови статистики за виконавцями.

---

## 2. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?

`$stdDevPop` обчислює стандартне відхилення для всієї генеральної сукупності.

Розрахунок базується на:

```text
N
```

`$stdDevSamp` використовується, коли дані розглядаються як вибірка з більшої генеральної сукупності.

Для нього використовується корекція:

```text
N - 1
```

У задачі з tempo використано `$stdDevPop`, тому що аналізуються всі доступні треки кожного жанру у поточному датасеті.

# Частина 3 — Аналітика через Aggregation Pipeline

Запити знаходяться у:

```text
queries/part3_aggregations.js
```

Реалізовано:

1. Top-10 виконавців за середньою популярністю;
2. розподіл треків за настроєм;
3. аналіз музичних жанрів за danceability, energy та valence.

---

## Завдання 1 — Top-10 виконавців

Для кожного артиста:

1. масив `artists` розгортається через `$unwind`;
2. треки групуються за артистом;
3. обчислюється кількість треків;
4. обчислюється середня популярність;
5. артисти з менш ніж 5 треками відсіюються;
6. результат сортується за середньою популярністю.

---

## Завдання 2 — Розподіл треків за настроєм

У завданні поняття `high` та `low` для `valence` і `energy` не мають конкретної числової межі.

Тому в реалізації використана межа:

```text
0.5
```

Класифікація:

| Valence | Energy | Mood |
|---|---|---|
| >= 0.5 | >= 0.5 | happy |
| < 0.5 | >= 0.5 | angry |
| >= 0.5 | < 0.5 | calm |
| < 0.5 | < 0.5 | sad |

Для класифікації використовується оператор:

```javascript
$switch
```

---

## Завдання 3 — Найбільш танцювальний жанр

Для кожного жанру обчислюються:

```text
avg_danceability
avg_energy
avg_valence
track_count
```

До результату включаються лише жанри, що мають щонайменше 100 треків.

---

## 1. Як зміниться результат при різних порогах кількості треків артиста?

Фактичний аналіз датасету показав:

```text
total_artists: 29858
artists_ge_5: 7154
artists_gt_50: 355
max_tracks: 510
```

При порозі:

```text
>= 5
```

у вибірці залишається:

```text
7154 artists
```

Якщо знизити поріг до:

```text
>= 1
```

у розрахунок потраплять усі:

```text
29858 artists
```

Це значно збільшить вибірку.

Водночас середня популярність артистів, які мають лише один або два треки, є менш репрезентативною. Наприклад, артист з одним дуже популярним треком може отримати дуже високе середнє значення, хоча даних про нього мало.

Якщо вибирати лише артистів з більш ніж:

```text
50 tracks
```

залишиться:

```text
355 artists
```

Це значно звужує вибірку та залишає лише артистів, для яких у датасеті є велика кількість треків.

Максимальна кількість записів для одного артиста:

```text
510
```

---

## 2. Що зміниться, якщо поріг жанру знизити зі 100 до 50?

Фактичні результати:

```text
total_genres: 114
genres_ge_50: 114
genres_ge_100: 114
min_tracks: 999
max_tracks: 1000
```

Отже, результат:

```text
не зміниться
```

Усі 114 жанрів містять від 999 до 1000 треків.

Тому і поріг:

```text
>= 100
```

і поріг:

```text
>= 50
```

пропускають всі жанри.

# Частина 4 — Індекси та оптимізація

Скрипт знаходиться у:

```text
queries/part4_indexes.js
```

---

## Завдання 1 — Аналіз запиту та індексація

Аналізувався запит:

```javascript
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": {
    $gte: 0.7
  }
}).sort({
  popularity: -1
});
```

Для нього створений складений індекс:

```javascript
{
  track_genre: 1,
  popularity: -1,
  "audio_features.danceability": 1
}
```

---

## Explain до створення індексу

Фактичний результат:

```text
stage: SORT
stage: COLLSCAN

nReturned: 354
totalKeysExamined: 0
totalDocsExamined: 113999
```

MongoDB виконувала:

```text
COLLSCAN
```

тобто повне сканування колекції.

Було перевірено:

```text
113999 documents
```

Після цього MongoDB додатково виконувала сортування через:

```text
SORT
```

---

## Explain після створення індексу

Фактичний результат:

```text
stage: FETCH
stage: IXSCAN

nReturned: 354
totalKeysExamined: 412
totalDocsExamined: 354
```

Після створення індексу MongoDB використовує:

```text
IXSCAN
```

замість:

```text
COLLSCAN
```

Кількість переглянутих документів зменшилася:

```text
113999 → 354
```

При цьому кількість результатів залишилася однаковою:

```text
354
```

Отже, змінився спосіб доступу до даних, але не результат самого запиту.

---

## Що змінилося у плані виконання?

### До індексу

```text
COLLSCAN
SORT
```

MongoDB переглядала всю колекцію.

### Після індексу

```text
IXSCAN
FETCH
```

MongoDB спочатку знаходить відповідні ключі через індекс і читає лише необхідні документи.

---

## Як зрозуміти, що індекс використовується?

Основна ознака — стадія:

```text
IXSCAN
```

У нашому випадку також:

```text
totalKeysExamined: 412
```

Це означає, що MongoDB перевіряла ключі індексу.

Ще одна важлива ознака — суттєве зменшення:

```text
totalDocsExamined
```

До індексу:

```text
113999
```

Після:

```text
354
```

---

# Завдання 2 — Індекс для музики для роботи

Для пошуку використовуються поля:

```text
explicit
audio_features.instrumentalness
audio_features.speechiness
```

Для них створений складений індекс.

Фактичний `explain("executionStats")`:

```text
stage: FETCH
stage: IXSCAN

nReturned: 16141
totalKeysExamined: 16602
totalDocsExamined: 16141
```

Наявність:

```text
IXSCAN
```

підтверджує використання індексу.

MongoDB знаходить відповідні записи через індекс, після чого виконує:

```text
FETCH
```

для отримання самих документів.

# Завдання 3 — Covered Query

Дано запит:

```javascript
db.tracks.find({
  track_genre: "pop",
  popularity: {
    $gte: 70
  }
});
```

Індекс із першого завдання містить:

```text
track_genre
popularity
audio_features.danceability
```

Фактичний `explain()`:

```text
stage: FETCH
stage: IXSCAN

nReturned: 317
totalKeysExamined: 317
totalDocsExamined: 317
```

Цей запит:

```text
не є covered query
```

Умови:

```text
track_genre
popularity
```

можуть бути перевірені безпосередньо через індекс.

Але запит не має проєкції та повертає повний документ.

Повний документ містить також поля, яких немає в індексі, наприклад:

```text
track_name
artists
album_name
audio_features
duration_ms
explicit
```

Тому MongoDB після `IXSCAN` все одно повинна звернутися до основної колекції.

Саме тому у плані є:

```text
FETCH
```

Також:

```text
totalDocsExamined: 317
```

а не:

```text
0
```

Для справжнього covered query MongoDB повинна мати можливість отримати всі поля, необхідні і для фільтрації, і для результату, без читання самого документа з колекції.

Тому даний запит не є покривним.

# Висновок

У межах роботи було:

- створено MongoDB Atlas cluster;
- завантажено Spotify Tracks Dataset;
- імпортовано дані до `tracks_raw`;
- створено документо-орієнтовану колекцію `tracks`;
- використано вкладений документ `audio_features`;
- перетворено `artists` на масив;
- реалізовано фільтрацію за вкладеними полями;
- використано `$unwind`;
- використано `$group`;
- використано `$avg`;
- використано `$stdDevPop`;
- використано `$switch`;
- створено складені індекси;
- виконано аналіз `explain("executionStats")`;
- порівняно плани виконання до та після індексації;
- проаналізовано covered query.

Найпомітніший результат оптимізації отримано для запиту з:

```text
track_genre = "pop"
danceability >= 0.7
```

До створення індексу MongoDB переглядала:

```text
113999 documents
```

Після створення індексу:

```text
354 documents
```

План виконання змінився з:

```text
COLLSCAN + SORT
```

на:

```text
IXSCAN + FETCH
```

Це показує, наскільки правильно підібраний індекс може зменшити обсяг даних, які MongoDB повинна перевірити під час виконання запиту.
